## 二、核心建议：下一步优先做什么

基于当前项目状态，建议后续开发按以下优先级推进：

### 建议一（最高优先级）：完成渠道需求计划剩余 4 个功能

**理由：**
- 这是最近投入最大的模块，已接近闭环
- 4 个剩余功能量小且边界清晰：滚动版本（后端约 100 行）、版本对比（后端约 80 行）、Excel 导出（后端约 60 行）、MySQL/Redis 迁移准备（已有详细文档 28 号）
- 完成这些后，整个"渠道需求计划"可以作为第一个完整交付的业务模块

**具体建议：**
- 滚动版本和版本对比可以一起做，因为它们共享周序列逻辑
- Excel 导出独立做，依赖已有的 xlsx 库
- MySQL 迁移准备先做仓储层抽象（不影响当前 JSON 功能），不急着切真库

### 建议二（高优先级）：做阶段 0 止血

**理由：**
- 安全隐患是最紧迫的问题，拖得越久风险越大
- 阶段 0 的工作量不大，但影响面广，越早做对其他模块干扰越小
- 具体来说只需要改 4-5 个文件

**具体建议：**
1. 修改 `.gitignore`，添加 `server/.env` 和 `server/local-data/*.json`
2. 将 `server/.env` 从 Git 跟踪中移除（保留本地副本）
3. 创建 `server/.env.example` 模板文件
4. 将 `server/index.js` 中的 JWT Secret 兜底值改为启动必须由环境注入
5. 检查所有前端页面是否已统一使用 `VITE_API_BASE`
6. 处理 `User_Credentials.md`（脱敏或移除）

### 建议三（中优先级）：做阶段 1 的订单主链收敛

**理由：**
- 订单双事实源是整个系统最核心的数据一致性问题
- 如果不收敛，后续所有驾驶舱、分析、报表都会口径分裂
- 这是"先止血再治本"的"治本"第一步

**具体建议：**
- 先做一次全量排查：找出所有仍在写 `biz.orders` 的代码路径
- 逐步冻结旧链写入，所有新订单统一走 `order_headers + order_lines`
- 旧页面改造为"读取新链的兼容视图"

### 建议四（中优先级）：补充最小自动化测试

**理由：**
- 当前每次改动只能靠 `npm run build` 和手动联调验证
- 随着模块增多，回归成本指数级增长
- 不需要全覆盖，先覆盖最核心的 4 条主链

**具体建议：**
- 先做后端核心链路的 API 测试：订单创建→审核→分配、库存锁定→释放、主数据治理申请→审批→生效、渠道需求计划创建→填报→提交→确认
- 测试目录建议建在 `server/tests/`，用最小依赖（如 Node 内置 assert 或 supertest）
- 前端测试可以稍后，优先保障后端数据正确性

## 三、不建议现在做的事

### 3.1 不建议立即切 MySQL/Redis

文档 23 号已经有非常清晰的判断：**当前适合启动数据库接入准备，不适合立即完成数据库切换。**

原因：
- 订单/库存事实源尚未统一，此时切库等于固化双口径
- 缺少数据访问层抽象，切库需要全项目范围改代码
- 缺少事务边界定义、迁移脚本、对账机制、回滚方案
- 建议先完成仓储层抽象（`server/repositories/` 目录），保持 JSON 和 MySQL 双模式可切换，先不切读写

### 3.2 不建议对 server/index.js 做大重构

当前 index.js 确实很大，但在完成核心主链收敛之前，大重构风险过高。建议先按"收口"策略：新增业务模块继续走独立文件（如 channelDemandPlan.js 的模式），逐步减少对 index.js 的追加。

### 3.3 不建议立即新建独立产品锁定期路由

产品锁定期当前放在渠道需求计划页面内（作为弹窗/抽屉），这是合理的。它是一个编辑权限控制工具，不是独立业务页面，独立建路由会增加导航复杂度而不增加业务价值。

## 四、中长期的架构建议

### 4.1 数据库化改造的温和路径

文档 28 号给出的 5 轮切换方案非常好，建议严格执行：

1. **第一轮**：只连通，不改读写
2. **第二轮**：迁移 JSON 到 MySQL，对账，但仍读 JSON
3. **第三轮**：双读校验（后台对比差异）
4. **第四轮**：低风险模块切读 MySQL
5. **第五轮**：正式切写

这样每一轮都有明确的验收标准和回滚路径。

### 4.2 仓储层抽象

建议在 `server/` 下建立 `repositories/` 目录，先为渠道需求计划建立 `channelDemandPlanRepository.js` 接口层和 `localJsonChannelDemandPlanRepository.js` 实现。这个改动不破坏现有功能，但为未来切 MySQL 铺好了路。

### 4.3 关于 Vue Beta 版本

文档 20 号提到了 Vue 版本风险。建议在阶段 3（补工程化）时评估迁移到 Vue 3 稳定版。当前 Beta 版本在演示环境风险可控，但不应进入生产。

### 4.4 关于财年周口径

`master.calendar` 当前为空，渠道需求计划的周序列按 ISO 周计算。如果业务财年周与 ISO 周不一致，建议尽早补充业务日历数据或导入财年周映射，避免后续数据口径问题。
