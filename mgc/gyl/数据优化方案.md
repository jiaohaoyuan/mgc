# SCMP 数据优化方案

审计范围：前端 44 个页面 + 后端 15 个模块 + 数据持久层。共发现 35+ 个可优化项，按影响面和实施成本分为三个梯队。

---

## 第一梯队：立即实施（高影响、低成本）

### 1. `nextId()` 改为 O(1) 计数器

**现状**：`localDb.js` 的 `nextId(rows)` 通过 `Math.max(...rows.map(r => r.id)) + 1` 取最大 ID，每次插入 O(n) 全量扫描。全项目调用 159 次。当数组万行级别时，每次插入都要遍历整个数组。

**问题**：`buildVersionMatrixRows`（channelDemandPlan.js:572）在 渠道×SKU×周 的三层嵌套循环中调用，10 渠道 × 50 SKU × 26 周 = 13000 次 O(n) 扫描，等效 O(n²)。

**方案**：在 `db.meta.next_ids` 中维护每个表的自增计数器。

```javascript
// localDb.js
const nextId = (db, tableKey) => {
  db.meta.next_ids = db.meta.next_ids || {};
  if (!db.meta.next_ids[tableKey]) {
    const rows = db.biz[tableKey] || db.master[tableKey] || [];
    db.meta.next_ids[tableKey] = rows.reduce((max, r) => Math.max(max, Number(r.id) || 0), 0) + 1;
  }
  return db.meta.next_ids[tableKey]++;
};
```

**影响**：所有插入操作从 O(n) 降至 O(1)，`buildVersionMatrixRows` 构建时间从秒级降至毫秒级。

---

### 2. 库存台账建立 `Map` 索引，消除 `findLedgerRow` 线性扫描

**现状**：`inventoryOps.js` 的 `findLedgerRow` 每次对 `inventory_ledger` 做 `Array.find()` 全量扫描，在一个调拨单的完整生命周期（提交→审核→出库→入库）中被调用 10+ 次。dispatch 时每个分配行再扫描一次。

**方案**：在 `updateDb` 回调入口处预构建索引 Map。

```javascript
const buildLedgerIndex = (db) => {
  const idx = new Map();
  arr(db.biz.inventory_ledger).forEach(row => {
    const key = `${row.warehouse_code}::${row.sku_code}::${row.batch_no}`;
    idx.set(key, row);
  });
  return idx;
};
```

**影响**：库存相关操作从每次 O(n) 降至 O(1)，调拨单生命周期整体从秒级降至毫秒级。

---

### 3. `buildTransferNo` / `buildSubmissionNo` 用计数器代替全量扫描

**现状**：每次创建调拨单或提报单，都扫描整个 `transfer_orders` 或 `channel_demand_submissions` 数组来找到当天最大序号。

**问题**：`dispatchSubmission`（channelDemandSubmission.js:279）在内层循环中为每个分配行执行一次全量扫描。200 行分配 = 200 次全量扫描。

**方案**：在 `db.meta` 中维护日期+前缀的序号计数器。

```javascript
const buildTransferNo = (db) => {
  const datePart = new Date().toISOString().slice(0, 10).replace(/-/g, '');
  db.meta.transfer_seq = db.meta.transfer_seq || {};
  const key = `TR${datePart}`;
  db.meta.transfer_seq[key] = (db.meta.transfer_seq[key] || 0) + 1;
  return `${key}${String(db.meta.transfer_seq[key]).padStart(4, '0')}`;
};
```

**影响**：O(n) → O(1)，dispatch 200 行时从 ~200 次全量扫描降至 0 次。

---

### 4. `refreshWarnings()` 改为按需触发，不再每次查询都重建

**现状**：`inventoryOps.js` 的 GET `/dashboard`、`/ledger/list`、`/transactions/list`、`/warnings/list` 都在响应前调用 `refreshWarnings(db)`，触发全量 `inventory_ledger` 扫描 + 日期计算 + 去重 + 整个 `inventory_warnings` 数组替换。**只读查询触发写操作**。

**方案**：预警改为在 `updateDb` 写操作后触发（入库、出库、调拨完成后），读查询直接返回已有的 `inventory_warnings`。

**影响**：读操作不再触发全量扫描和写 I/O，dashboard 首屏响应时间减半。

---

### 5. `channelDemandPlan.js` 版本对比避免多次扫描 `channel_demand_plan_data`

**现状**：`compareVersionCore` 用两次 `.filter()` 分别取源版本和目标版本数据行（lines 998-1002），然后 `decorateVersionRow` 在 `map()` 中对每个版本再做一次 `.filter()` 统计锁定格数。

**方案**：一次 `.filter()` 遍历将所有相关数据行收集好，然后分组构建 Map。

```javascript
const allData = arr(db.biz.channel_demand_plan_data);
const byVersion = new Map();
allData.forEach(row => {
  if (!byVersion.has(row.version_code)) byVersion.set(row.version_code, []);
  byVersion.get(row.version_code).push(row);
});
const sourceRows = byVersion.get(sourceCode) || [];
const targetRows = byVersion.get(targetCode) || [];
```

**影响**：版本对比从 3 次全量扫描 → 1 次遍历，当数据 100K+ 行时减至 1/3 时间。

## 第二梯队：短期实施（中影响、中成本）

### 6. 操作日志写入合并

**现状**：`appendOperationLog` 和 `appendSecurityLog` 每次调用都触发独立的 `updateDb()` → `saveDb()` → 整文件 `JSON.stringify` + 写入。一个 API 请求如果既改数据又写日志，整个 `db.json` 被序列化写入两次。

**方案**：操作日志收集到内存缓冲区，在请求结束时一次性写入。或在 `updateDb` 回调中同时追加日志，共用一次 `saveDb()`。

**影响**：I/O 压力减半，尤其对高频操作（如翻页查询日志、批量状态变更）。

---

### 7. 主数据（master.*）按请求范围缓存 Map

**现状**：`getChannelProvince`、`getWarehouseProvince`、`listActiveLv2Channels`、`listActiveSkus` 等函数在同一个请求内被反复调用，每次都做 `arr(db.master.xxx).find()` 线性扫描。

**方案**：在每个路由 handler 入口处预构建 `master` 表索引 Map，同一请求内共享。

```javascript
// 在 readDb 或路由 middleware 中
const masterIndex = {
  channelByCode: new Map(arr(db.master.channel).map(c => [c.channel_code, c])),
  skuByCode: new Map(arr(db.master.sku).map(s => [s.sku_code, s])),
  warehouseByCode: new Map(arr(db.master.warehouse).map(w => [w.warehouse_code, w])),
};
// 注入到 req 或传参
```

**影响**：所有 `.find()` 调用从 O(n) 降至 O(1)，对 inventoryOps 和 demand submission 效果显著（每次仓库匹配都复用）。

---

### 8. RBAC 权限上下文缓存到 JWT claims

**现状**：`buildRbacContext` 在每个 API 请求中做 4 次数组扫描（account_roles → roles → role_pages → pages）。对于高频访问的 API，这是纯浪费的重复计算。

**方案**：登录时将权限路径列表编码到 JWT 的 claims 中（通常是字符串数组，体积可控），请求时直接从 token 解析，无需查数据库。

**影响**：每个请求省去 4 次数组扫描，对需要权限校验的 30+ API 路径均有收益。

---

### 9. 消除 `ensure*Structures` 冗余调用

**现状**：`ensureChannelDemandPlanStructures(db)` 在 `channelDemandPlan.js` 的 22 个路由 handler 中各自调用。每次调用都遍历 15+ 个数组执行 `ensureArray`。`ensurePlatformStructures` 在每次 `loadDb()` 缓存 miss 时执行 50+ 项检查。

**方案**：将 structure ensure 移到 `updateDb` 的入口处（写操作前），读操作不再执行。

**影响**：读查询不再执行数组安全校验，每个 GET 请求省去 ~15 次 `arr()` 调用。

同上，应合并修。

### 11. 前端：UserManage / RoleManage / PostManage 翻页改为服务端分页

**现状**：这些页面通过 `appStore.fetchSystemData()` 一次性拉取所有用户/角色/岗位到 Pinia store，然后在组件内用 `computed` + `slice()` 做客户端分页。

**方案**：管理页面传 `page` / `pageSize` / `keyword` 参数给 API，后端做服务端分页。

**影响**：当用户数从 50 → 5000 时，初始加载和搜索不会退化。

---

### 12. 前端：IntelligentOrdering 的 `.find()` 改为 `computed` Map

**现状**：`getSkuDetails` 等函数每次调用都 `products.value.find(p => p.sku === skuCode)`，在渲染循环中重复扫描。

**方案**：

```typescript
const productMap = computed(() => 
  new Map(products.value.map(p => [p.sku, p]))
);
// 使用时
const sku = productMap.value.get(skuCode);
```

**影响**：渲染循环中的查找从每次 O(n) 降至 O(1)。

## 第三梯队：中长期规划（高影响、高成本）

### 13. `localDb.js` 的 JSON 文件存储升级为 SQLite

**现状**：整个 `db.json` 在每次读/写时完整解析/序列化。当 `inventory_ledger` 累积 10 万+ 行时，文件可达 50MB+，`JSON.parse` 耗时 500ms+，`JSON.stringify` 耗时 800ms+，全部在主线程同步执行，阻塞事件循环。

**方案**：引入 `better-sqlite3`（同步 SQLite，与现有同步模式兼容），分表存储。改动集中在 `localDb.js`，其他模块的 `readDb/updateDb` 接口保持不变。

**迁移路径**：
1. 先用 SQLite 替换 `db.json`，保持读取接口不变
2. 逐步将 `.filter()` 重写为 SQL WHERE 查询
3. 将 `nextId` 替换为 SQLite AUTOINCREMENT

**影响**：所有读/写操作不再全量序列化，支持索引查询，并发安全。

---

### 14. 库存台账分区存储（热/冷数据分离）

**现状**：`inventory_ledger` 中所有批次数据混合存储，包括已售罄、已过期批次。

**方案**：将 `inventory_ledger` 拆分为 `inventory_ledger_active`（available_qty > 0）和 `inventory_ledger_history`（available_qty = 0），日常操作只查询 active 表。

**影响**：库存查询的数据集缩小 80%+。

---

### 15. 前端：ManagementCockpit 的 7 个并行 API 合并为 1 个聚合端点

**现状**：`ManagementCockpit.vue` 的 `onMounted` 中并行调用 7 个独立的 API。浏览器 HTTP/1.1 限制 6 个并发连接，部分请求排队等待。

**方案**：后端新增 `GET /api/management-cockpit/dashboard` 聚合端点，一次性返回所有 7 个维度的数据。

**影响**：从 7 次往返 + 7 次 `readDb()` + 7 次 JSON 解析 → 1 次往返 + 1 次 `readDb()`。

---

### 16. ChannelDemandPlan 版本编辑的批量保存

**现状**：用户每次在编辑表格中修改一行数据，触发 `PUT /version/:code/data` 写入全量数据行。一次编辑会话可能触发数十次完整写入。

**方案**：前端维护变更集，用户离开页面或点"保存"时一次性提交。

**影响**：大幅减少写 I/O，改善编辑响应速度。
