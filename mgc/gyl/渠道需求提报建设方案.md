# 渠道需求提报 — 建设方案

## 一、两个概念的区别

在开始设计之前，先理清「渠道需求计划」和「渠道需求提报」的本质差异。

### 渠道需求计划（已有）

**定义**：一个需求总量规划文档。它回答的问题是——"每个渠道，在未来的每个周，需要多少货？"

**核心数据**：计划行 `(渠道 × SKU × 周 → 需求量 plan_value)`，比如：

> 华东经销商渠道，2026年第18周，需要纯牛奶(SC-01001) 共 5,000 箱

**层级**：计划 → 版本 → 数据行，是一个聚合层面的"要多少"。

**操作主体**：计划管理员制定计划版本，各渠道负责人确认本渠道数据，最终由管理员锁定。

**输出**：一份确认后的需求量总表。

### 渠道需求提报（待建）

**定义**：一个供应分配执行文档。它回答的问题是——"确认好的需求量，由哪几个仓库、各出多少货来满足？"

**核心数据**：分配行 `(渠道 × SKU × 周 → 仓库 → 分配量 allocation_qty)`，比如：

> 华东经销商渠道，2026年第18周，纯牛奶(SC-01001) 共需要 5,000 箱
> → 杭州仓出 3,000 箱（60%），上海仓出 2,000 箱（40%）

**层级**：已确认计划版本 → 分配明细（仓库维度展开），是一个执行层面的"谁出多少"。

**操作主体**：供应链调度员或仓配运营人员，基于库存实况决定仓库分配比例。

**输出**：一份可执行的调拨/发货指引。

### 一句话总结

| 维度 | 渠道需求计划 | 渠道需求提报 |
|------|-------------|-------------|
| 核心问题 | 要多少？ | 从哪出？ |
| 数据粒度 | 渠道 × SKU × 周 | 渠道 × SKU × 周 × 仓库 |
| 输入 | 市场/渠道上报的需求量 | 已确认的计划量 + 库存实况 |
| 输出 | 需求总表 | 调拨/发货指引 |
| 操作角色 | 计划管理员、渠道负责人 | 仓配运营、供应链调度 |
| 与库存的关系 | 不直接关联 | 直接依赖仓库实时库存 |

## 二、整体架构设计

### 2.1 数据流

```
┌──────────────────────────┐
│ 渠道需求计划 (已确认版本)  │
│ plan_value: 渠道需求总量   │
└──────────┬───────────────┘
           │ 1. 引用已确认版本
           ▼
┌──────────────────────────┐
│ 渠道需求提报 (新建)        │
│ - 创建提报单              │
│ - 按 SKU 匹配仓库         │
│ - 计算建议分配比例         │
│ - 人工调整/确认           │
└──────────┬───────────────┘
           │ 2. 生成分配明细
           ▼
┌──────────────────────────┐
│ 下游执行                  │
│ - 库存锁定/预留           │
│ - 调拨单创建              │
│ - 发货通知               │
└──────────────────────────┘
```

```javascript
  updated_by: string,
  updated_time: string
}
```

### 2.3 仓库匹配策略

**第一阶段（当前方案）**：最近两个仓库 + 可调比例

顺序：本省仓库 → 邻省仓库，按可用库存降序排列，取前 2 个。

**默认分配比例**（可调）：
- 主仓库（距离近、库存多）：70%
- 次仓库：30%

分配逻辑：
1. 确认计划版本后，创建提报单
2. 遍历所有 `(渠道, SKU, 周)` 需求行
3. 对每行，查找该 SKU 有库存的仓库，按距离（本省→邻省）和可用库存排序
4. 取前 2 个仓库，分别计算 `plan_value × 0.7` 和 `plan_value × 0.3`
5. 若仓库可用库存不足，自动缩减至库存上限，缺口留给另一仓库或标记短缺
6. 提交前，调度员可手动调整每个仓库的分配量和比例

**第二阶段**（可后续扩展）：
- 考虑仓库产能、运输时效、保质期批次先进先出
- 多仓库智能分配算法
- 运输成本优化

## 三、功能页面设计

### 3.1 主页面：渠道需求提报列表

**位置**：侧边栏「业务运营」分组下，放在「渠道需求计划」下方

**功能**：
- 提报单列表（编号、关联计划、关联版本、状态、创建时间、操作人）
- 新建提报单（选择已确认的需求计划版本）
- 查看/编辑/确认/下发
- 筛选：状态、计划、时间范围

### 3.2 提报编辑页（核心页面）

采用**抽屉页面**方式（与现有需求计划的版本编辑页风格一致）：

**上半部分**：提报概览
- 关联计划信息（计划名称、版本、周范围）
- 分配进度统计（已足额分配行数 / 总行数）

**下半部分**：分配明细表格

表格列设计：

| 列名 | 说明 |
|------|------|
| 渠道 | 二级渠道名称 |
| SKU | 商品编码+名称 |
| 周 | 需求周次 |
| 计划需求量 | 来自需求计划的 plan_value |
| 杭州仓分配 | 可编辑数字输入框 + 比例 % |
| 上海仓分配 | 可编辑数字输入框 + 比例 % |
| 已分配合计 | 自动汇总 = 仓1 + 仓2 |
| 缺口 | 计划量 - 已分配合计，红色高亮 |
| 状态 | 足额/缺额 标签 |

交互行为：
- 每个仓库列的分配量可手动输入
- 修改一个仓库的分配量，自动重算比例和另一仓库的分配量（保持比例对称）
- 若某仓库库存不足以支撑当前分配量，该单元格标红并 tooltip 提示
- 提供"一键填充建议比例"按钮，对所有行按当前默认比例（70/30）预填，不足则自动调整
- 支持按渠道/按SKU切换查看维度

**底部操作栏**：
- 保存草稿
- 一键填充建议分配
- 提交确认
- 导出发货指引（Excel）

### 3.3 仓库库存快照面板（侧边辅助）

在提报编辑页的侧边，展示当前提报涉及的所有 SKU 在各仓库的实时库存概况，帮助调度员做决策。

### 6.2 核心算法：仓库匹配与分配

```javascript
// 伪代码：单行分配逻辑
function autoAllocateOneLine(db, line, warehouseRatioConfig) {
  const { sku_code, plan_value, lv2_channel_code } = line;
  const ratio = warehouseRatioConfig.defaultRatio; // 如 [0.7, 0.3]

  // 1. 查找该 SKU 有库存的仓库
  const warehouses = db.biz.inventory_ledger
    .filter(r => r.sku_code === sku_code && r.available_qty > 0)
    .map(r => ({
      warehouse_code: r.warehouse_code,
      warehouse_name: r.warehouse_name,
      available_qty: r.available_qty,
      priority: calcPriority(r, lv2_channel_code) // 本省=0, 邻省=1, 其他=99
    }));

  // 2. 按优先级和可用库存降序排列，取前2个
  const sorted = sortByPriority(warehouses).slice(0, 2);

  // 3. 按比例分配
  const allocations = sorted.map((wh, i) => {
    const target = Math.round(plan_value * ratio[i]);
    const actual = Math.min(target, wh.available_qty); // 不超库存
    return { ...wh, allocation_qty: actual, ratio: ratio[i] };
  });

  return allocations;
}
```

## 八、关键决策点（待确认）

在开始开发前，建议先明确以下几个问题：

1. **仓库数量上限**：当前设定每个 SKU 取最近 2 个仓库，未来是否需要扩展到 N 个？
2. **默认分配比例**：70/30 是否合理？是否需要按仓库类型（常温/冷藏/冷冻）区分默认比例？
3. **库存不足时的策略**：A) 自动缩减至库存上限，标记缺口；B) 不让提交，强制人工处理。倾向哪个？
4. **提报确认后的下游动作**：确认后是仅生成发货指引供参考，还是自动创建调拨单/锁定库存？
5. **权限控制**：哪些角色可以操作提报？是否需要与需求计划相同的渠道粒度权限？
